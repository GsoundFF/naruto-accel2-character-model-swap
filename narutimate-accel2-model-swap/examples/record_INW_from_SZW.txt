================================================================================
背景：战斗中开奥义演出时，角色变回原版井野模型。奥义演出加载的并不是战斗用的
/PL/2INWBOD1.CCS，而是另外的模型文件，需要逐一找出并做同样手术。

【第1步 → MOD5：换 /PL/MODEL/2INWBOD1.CCS（结果：奥义仍无变化）】
原因猜测：奥义用"MODEL"变体（战斗级骨架、无 ANM、身材体+贴图+Stream）。
  - MODEL/2INW 结构：CMP_2inw00t0(25骨) + MDL_2inw00t0 body(rec 61260)
    + BoundingBox + CMP_2inw05t0(25骨) + MDL_2inw05t0 body(同数据第二份，
    材质 MAT_clut5) + CMP_2inwh00t0(9骨头发) + CLT×3 + TEX。
  - MODEL/2SZW：CMP_2szw00t0(34骨) + body（consumed=52012, rec=53152,+1140）
    + TEX/CLT×3。无 05、无头发。
  - 名字编号巧合对齐：两文件 body=98 / MAT=99 / TEX=100；仅 CLUT 不同
    （SZW 102/103/104 → INW 222/223/224）。05 body=199、MAT_clut5=200、
    头发=220（MODEL 头发 rec=7924、consumed=7804、配套惯例+120）。
  - SZW MODEL body lookup 与战斗版顺序不同（[11,4,3,18,19,23,24,20,21,22,12,
    13,5,6,30,28,29,8,9,7,10,25,26,27]），按"静音位置→井野位置"映射重写为
    [11,4,3,14,15,19,20,16,17,18,12,13,5,6,3,3,3,8,9,7,10,21,22,23]。
  - 替换：00 body（mat/idx 不变）、05 body（idx→199、mat 99→200）、
    头发置空（idx=220）、TEX（clut 102→222）、CLT×3（102/103/104→222/223/224）。
  - 新文件 199,464 B，gz 58,468 ≤ 原 69,994 → 原位补丁 → MOD5.iso。
  - 结果：用户测试进战斗正常，但奥义仍显示原版井野 → MODEL 文件不是奥义模型。

【第2步 → MOD6：换 /PL/1INWBOD1.CCS（1P 高模，选人+奥义共用）】
由排除法（能显示奥义的文件必须对全角色都存在）锁定 /PL/1INWBOD1.CCS
（59骨(INO)/64骨(SZW) 高模，带 eye1/eye2/mou1 眨眼/嘴部独立件与独立贴图）。
  - 结构：body(MAT全190) + 3个刚性面部件(自贴图 TEX_1*eye1/mou1, type I4,
    CLUT 196/197) + 影子 + 空骨模型。索引全部对齐：body=189, MAT=190,
    bodyTEX=191, CLT=193/194/195, eyeTEX INO120/SZW122, mouTEX INO127/SZW129,
    CLT 196/197 两边同名同号。
  - 骨架按名字映射 SZW(64)→INO(59)：0-11同名恒等；12-14 tail→2(pelvis)；
    15-17 spine1/neck/head→12/13/14；18-24马尾→15-21；25/26/27
    eye2/eye1/mou1→23/22/24；28-57 l/r 肩臂手指链→25-54；58-60 muffler→55-57；
    61-63 cloth/body→58。SZW lookup(46项)→新表(46项，含重复2)。
  - 换：body 数据(仅 lookup 重映射)、body TEX/CLT×3、eye/mou TEX+CLT、
    3个面部件；影子/空模型/对象/骨架/Stream 保留井野的。
  - 新文件 505,152 B，gz 65,303 ≤ 原 81,276 → 原位补丁。

【MOD6 第一版卡进战斗 → 原因与修复（重要教训）】
初版把眼部刚性件(eye1/eye2/mou1) 的 parent[28] 字段误写成 OBJ 索引(26/27/28)。
实测：该字段引用的是配套 "_0" 模型块（MDL_1inw00t0 eye1_0 等，索引
118/122/125），材质[32]=119/123/126（材质这步本来就对）。parent 写成 OBJ →
引擎解析到错误对象 → 1P 模型加载即崩 → 选人后进战斗卡死。
修复：移植 SZW 面部几何时 [0]名字与几何来自 SZW，[28]parent 与 [32]材质
一律保留井野原件的值（118/122/125、119/123/126）。
修复版验证：eye parents/mats = 118/122/125 + 119/123/126、194 块结构完整。

【最终产物（已验证）】
MOD6.iso = MOD4.iso 副本 + 两处原位补丁：
  /PL/MODEL/2INWBOD1.CCS  69,994B @ 595,259,392（= (210454+3+80197)×2048）
  /PL/1INWBOD1.CCS       81,276B @ 522,053,632（= (210454+3+44452)×2048）

三、CCS 文件格式要点（版本 0x123，CCSF2inwbod1）
--------------------------------------------------------------------------------
1) 布局：文件头 + 索引表(路径表32B/名字表30B+u16路径) + Setup 区 +
   一系列"块" + Stream 块(8+4字节) + 尾部帧数据(12字节)。
   井野文件头+索引+Setup = 107,028 字节；共 5,974 个块；总长 1,065,844。

2) 每个块：8 字节头 [type u16][0xCCCC u16][长度 u32×4] + 数据。
   解析是"块头驱动"的（按类型读内容，不按记录长度跳）。
   注意两个例外惯例（记录长度比实际数据大）：
     Model 块         记录 = 实际网格数据 + 1140（"同伴块"逻辑长度）
     RGBA32 Texture 块 记录 = 实际 + 200
   重建文件时必须保留这个惯例（脚本里已处理）。

3) Model 块数据（Deformable）：
   头 52 字节 = u32名字编号 + f32顶点缩放 + u8类型 + u8标志 + u16网格数
              + 8字节杂项 + outline颜色4 + outline宽度4 + lookupList(4对齐)
   然后每个 DeformableMesh（u32材质编号, u32顶点数vc, u32变形顶点数dc）：
     dc==0 单权重：u32 骨骼槽位 + 坐标int16×3×vc + 4对齐 + 法线int8×4×vc
                   + UV int16×2×vc
     dc>0  多权重：vp 表 dc×(int16 x,y,z,param) + 法线 dc×4 + UV vc×4
         param：bits15-10 骨骼槽位 / bit9 "还有下一项" / 低9位权重

4) ★ 最重要的发现：Model 里的"骨骼编号"其实是 lookupList 的槽位！
   lookupList 长度=N，内容=该模型用到的骨架位置列表；顶点槽位恒为 0..N-1 前缀。
   证据：两个 body（21/24项）与头发（5项）的槽位范围都恰好=0..N-1；
   1262 顶点的大网格槽位23 → lookup[23]=13=头（若按骨架位置解释=右手小指，荒谬）。
   因此换模型时：顶点槽位一个都不改，只把 lookupList 内容按骨架映射重写。

5) 骨架（Clump 块 CMP_2inw00t0 trall = 25 根）：
   0 trall, 1 根, 2 footsteps, 3 pelvis, 4 spine, 5 l thigh, 6 l calf, 7 l foot,
   8 r thigh, 9 r calf, 10 r foot, 11 spine1, 12 neck, 13 head,
   14 l clavicle, 15 l upperarm, 16 l forearm, 17 l hand, 18 l finger0,
   19 r clavicle, 20 r upperarm, 21 r forearm, 22 r hand, 23 r finger0, 24 body
   静音骨架 34 根：0-13 相同；14-17 马尾辫；18-23 l clavicle..r clavicle；
   24-27 r upperarm..r finger0；28-30 tail/tail1/tail2(白大褂后摆)；31-33 cloth/body。

6) 名字表编号（换数据时改这些）：
   井野：MDL_2inw00t0 body=3172  MAT_clut=3173  TEX_2inwbody=3174
         CLT_2inwbody=3209  c1=3210  c2=3211  头发MDL_2inwh00t0 body=3194
   静音：MDL_2szw00t0 body=4671  MAT_clut=4672  TEX_2szwbody=4673
         CLT_2szwbody=4752  c1=4753  c2=4754

四、替换内容（井野 body 文件内做的三处手术）
--------------------------------------------------------------------------------
1) MDL_2inw00t0 body（原60,120B）← 静音 MDL_2szw00t0 body（55,784B）：

     原 [11,4,3,18,19,23,24,20,21,22,12,5,6,30,28,29,8,9,7,10,25,26,27,13]
     新 [11,4,3,14,15,19,20,16,17,18,12,5,6,3,3,3,8,9,7,10,21,22,23,13]
   骨架位置映射：0-13 恒等；14-17马尾→13头（本lookup不含，防御）；
     18→14,19→15,20→16,21→17,22→18,23→19；24→20,25→21,26→22,27→23；
     28,29,30(衣摆tail)——井野无尾巴→3 pelvis(随骨盆摆动最自然)；31-33→24。
   19 个子网格的材质编号 4672→3173（逐个断言原值后改写）
   顶点槽位数据零改动；记录长度 = 55,784 + 1140 = 56,924
2) TEX_2inwbody ← 静音 TEX_2szwbody（65,564B 相同尺寸）：
   名字编号 4673→3174；数据内 CLUT 指针 4752→3209；记录 +200

   名字编号 4752/4753/4754→3209/3210/3211，其余数据整体复制

   28 字节空模型头（如 MDL_2inw00t0），名字编号改 3194；记录=28+120=148。
   目的：避免井野发型与静音脸部/刘海叠在一起。
   （静音的马尾不在 BOD1 文件里，需后续单独处理头发文件。）

六、跑过的坑 / 经验（照做可避免）
--------------------------------------------------------------------------------
1) 【最大教训】cvm_tool mkcvm 不给 -p 密码 = 输出"未加密卷"
   （把 CVMH 加密标志 0x10 清零）。游戏 ROFS 加载器只认加密卷 →
   游戏进程起不来 → 直接黑屏（表现像"镜像坏了"，实际是卷格式问题）。
   原版 CVM 和之前能进游戏的版本全部是加密卷（flags_30=0x10）。
   → 结论：在不知道 ROFS 密码的情况下，绝对不要重建 CVM。
   → 正确做法：CVM 的 ZONE 负载（ISO 数据区）是明文的，直接原位改文件字节。

2) 原方案"改顶点骨骼编号"是错的：顶点编号是 lookupList 槽位（见第三节4），
   照着旧理解改顶点会把模型绑到错误的骨头上。

3) 解析器对 Model/Texture 块"记录长度>实际"的惯例（+1140/+200）要在重建时保留，
   否则引擎/解析器行为可能不一致（保留后往返测试逐字节一致）。

4) 井野/静音 body 网格数据长度不同没关系：重建按实际长度写即可（块头驱动）。

5) 奥义修复踩坑：Rigid 面部件(eye1/eye2/mou1) 数据里的 parent[28] 不是"父骨
   OBJ"，而是同名配套 "_0" 模型块的编号（如 MDL_1inw00t0 eye1_0）；移植数据时
   parent/mat 一律保留目标文件原值，只改名字编号与几何。
